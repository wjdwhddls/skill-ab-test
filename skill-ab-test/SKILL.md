# Skill Analysis and A/B Test

아직 설치하지 않은 GitHub 스킬 하나를 도입 전에 전체적으로 이해한다. **폴더와 파일 → 조건별 작동 흐름 → 도구·입출력·환경 전제 → 실제 A/B 실행 → 메인의 판단**을 한국어 HTML로 연결한다. A/B 비교는 이 분석의 일부다. 처음 보는 사용자도 각 파일이 왜 있고, 어떤 요청에서 무엇을 읽거나 실행하며, 이번 시험에서 어디까지 확인했는지 알 수 있게 만든다.

## 역할

- **메인:** 전체 소스 구조와 작동 방식 분석, 질문과 기준 사전 확정, 두 실행의 실제 로그 검토, 선언된 절차와 관측 행동 연결, 양쪽 발췌 선택, 개선·악화·차이 없음·판단 불가 판정, HTML 요약 작성.
- **응답 에이전트 두 개:** 동일 과제를 각각 수행한다. 자기 결과를 비교·채점하지 않는다.
- **도구:** 스킬 상태를 조회하고 실제 이벤트를 보존·검증·표시한다. 의미나 품질을 판정하지 않는다.

## 모든 사용자에게 적용하는 출력 계약

스킬 폴더 전체에 포함된 `scripts/`와 `assets/`가 화면과 상호작용을 결정한다. 메인은 실행 폴더의 계획·소스 분석·실제 기록·근거에 따른 리뷰·캡처 자료를 준비하고, 설치된 `trace_report.py`로 최종 HTML을 생성한다. 일반 실행 중 스킬 코드·템플릿·생성 HTML을 직접 고치거나 별도 래퍼로 검사를 건너뛰지 않는다. 필요한 파일이나 실행 조건이 없으면 부족한 조건을 보고한다. 스킬 자체의 개선 요청은 별도의 유지보수 작업이다.

같은 스킬 버전과 같은 입력 자료에서는 같은 HTML이 나와야 한다. 새 실행의 답변·로그·시간·토큰과 메인의 근거 선택·판정은 달라질 수 있다. 스킬의 지침은 의미 판정을 자동 점수로 바꾸지 않는다. 바탕체 계열 글꼴은 사용자의 설치 글꼴에 따라 대체되며, 원본 화면은 실제 캡처 가능한 범위에서만 제공한다. 예시의 내용·수치·캡처 유무까지 동일하다고 보장하지 않는다.

## 기본 실행: 전체 구조 분석과 로그 기반 비교

[skill-analysis.md](references/skill-analysis.md)와 [trace-protocol.md](references/trace-protocol.md)를 읽고 진행한다. 전자는 소스 분석과 `skill-analysis.json`, 후자는 실험 통제·실행·판정·캡처 계약이다.

실행 환경은 Python 3.11 이상과 사용 가능한 Codex CLI를 요구한다.

1. **미설치 확인·원문 고정:** GitHub 링크에서 선택한 스킬의 하위 폴더 전체를 `source/`에 경로와 바이트 그대로 보존하고 commit·출처·파일 목록을 기록한다. 저장소 전체를 무조건 수집하지 않는다. 스킬 밖 참조가 필요하면 그 범위와 수집 여부를 명시한다. 현재 설치 목록·알려진 로컬 스킬 경로에서 이름/이름공간/원문 해시가 겹치면 이번 비교를 중단한다. 기존 스킬을 지우거나 잠깐 끄는 시험은 범위에서 제외한다.
2. **메인이 전체 구조 분석:** `SKILL.md`뿐 아니라 참조·스크립트·메타데이터·자산을 조사해 `skill-analysis.json`을 작성한다. 모든 보존 파일의 역할·읽는 조건·파일 간 관계, 선언된 분기와 입출력, 서비스·실행 도구·의존성, 환경 전제를 원문 근거에 연결한다. 파일 내용만으로 도구 호출이나 절차 수행을 확정하지 않는다. 분석 파일과 평가 기준은 두 응답 에이전트의 작업 폴더 밖에 두고 전달하지 않는다.
3. **과제 고정:** 대표 상황·복합 조건·정보 부족 상황 3개와 판단 기준을 `trace-plan.json`에 작성한다. 공통 과제에는 사용자 목표와 동일 자료를 주고 스킬의 절차·정답을 알려주지 않는다. 실제 자료 탐색이나 누락 확인 등 차이를 관찰할 수 있는 과제를 고른다. 실행 범위는 텍스트 응답과 필요한 읽기 작업이며, 이번 과제로 다루지 못하는 분기는 분석에 남긴다.
4. **실제 OFF/ON 실행:** `run_trace_pair.py`로 새 Codex 프로세스 두 개를 실행한다. 두 조건에서 발견된 다른 스킬은 동일하게 비활성화하고 B의 별도 작업 폴더에만 대상 스킬을 임시로 준비한다. A에는 등록하지 않고 대상 파일 읽기도 차단한다. 실행별 설정만 사용하며 전역 설치나 설정은 변경하지 않는다. 별도 플러그인 노출도 두 실행에서 끈다. 양쪽의 `skills/list`와 실제 파일 읽기 허용/차단 검사를 통과한 뒤에만 모델을 실행한다.
5. **실행 증거 수집:** `codex exec --json` stdout을 `events.jsonl`로 그대로 보존하고 수신 시각, stderr, 최종 답변, 프롬프트, 활성 목록과 해시를 함께 남긴다. B에는 고정 스킬 파일을 실제 읽도록 지시해 본문 열람을 로그에서 확인한다. 이 로딩 동작 자체를 품질 개선으로 채점하지 않는다.
6. **메인이 연결하고 비교:** 실제 로그를 읽어 분석의 각 단계·도구에 관측 근거를 붙이고, 품질 판정은 `trace-review.json`에 작성한다. 선언된 절차, 실제 파일 열람, 구체적 도구 호출, 출력에서 확인되는 준수를 구분한다. `report_scope.confirmed`에는 양쪽 근거로 확인되는 차이, `report_scope.unknown`에는 이번 해석에 직접 영향을 주는 관찰 한계만 쓴다. 각 판정에 양쪽 이벤트 행 또는 답변 발췌를 연결한다. 답변이 같아도 실행 절차 차이는 별도로 기록한다. 로그에 없는 내부 사고나 단계는 추정하지 않는다.
7. **전체 이해 대시보드:** `trace_report.py`로 `trace-report.html`을 만든다. 밝은 글래시 화면의 첫 탭에서 A/B 전체 실행 흐름을 나란히 보여주고, 비교 항목 하나를 선택하면 양쪽 실제 호출·입력·반환 로그가 함께 열린다. 하이라이트는 메인이 고른 정확한 원문 발췌에만 적용한다. 관련 원본 화면 캡처를 연결하고, 스킬 구조·선언된 절차·도구·최종 응답·판정·조건은 보조 탭으로 유지한다. 원문과 실행 순서는 그대로 보존하며 서로 다른 이벤트를 순서만으로 대응시키지 않는다. 본문은 바탕체, 명령·JSON은 고정폭 글꼴을 사용한다. 판정 개수는 승률·총점으로 바꾸지 않는다. [화면 구성 규약](references/trace-protocol.md#6-보고서-구조와-측정값)을 따른다.
8. **원본 로그 화면 촬영:** 원래 에이전트 UI나 터미널의 실행 로그를 실제로 촬영한다. 해당 화면을 사용할 수 없으면 원본 `events.jsonl`을 브라우저에서 직접 연 화면을 촬영하고 ‘종료 후 원본 파일 열람’임을 명시한다. 비교 HTML 화면 캡처는 디자인 검수용이며 원본 로그 캡처로 사용하지 않는다. `native_captures.py`에 실제 화면 종류·로그 파일·행 범위·촬영 시각을 등록하고 HTML을 재생성한다. 원래 앱 화면을 확보하지 못한 사실도 관찰 한계에 넣는다.

`skill_root`는 지금 읽은 이 파일의 부모 폴더, `run_dir`는 이번 실행 폴더의 절대 경로다.

```bash
python3 "$skill_root/scripts/run_trace_pair.py" "$run_dir"
# 메인이 skill-analysis.json에 실제 관측 연결, trace-review.json 작성
python3 "$skill_root/scripts/trace_report.py" "$run_dir"
# 캡처 등록 등 모든 자료 반영 후, HTML을 직접 편집하지 않았는지 확인
python3 "$skill_root/scripts/trace_report.py" "$run_dir" --check
```

`--check`는 현재 자료와 설치된 렌더러의 결과를 바이트 단위로 비교하며 파일을 쓰지 않는다. 불일치하면 원인 자료를 확인하고 같은 렌더러로 재생성한다. 이 검사는 HTML 일치 여부를 확인하며, 메인의 의미 판정이나 설치된 패키지의 배포 출처까지 인증하지는 않는다.

## 직접 측정한 기록만 표시

용어 설명이나 고정된 네 개념 표를 넣지 않는다. 소스 구조와 선언된 지시는 원문에, 실제 도구 호출·파일 열람·실행 상태·시간·토큰은 로그 또는 프로세스 기록에 연결해 표시한다. 선언된 서비스 목록을 실제 사용량처럼 표시하지 않는다. 비교 수치는 양쪽 모두 측정된 항목만 사용하며, 누락값을 0으로 바꾸지 않는다. 측정된 0은 그대로 보존한다.

사용 한도·잔여량·전체 비용은 실제 출처·측정 시점·단위·집계 범위를 확보했을 때만 쓴다. 자료가 없으면 해당 항목 자체를 생략하며 ‘미측정’ 카드나 개념 설명으로 채우지 않는다. 토큰으로 한도나 실제 요금을 추정하거나, 사람의 검토·수정 시간을 빠뜨린 값을 전체 비용으로 부르지 않는다. 캐시 입력은 전체 입력에 다시 더하지 않으며 단발 시간 차이를 스킬의 인과 효과로 단정하지 않는다.

## 해석과 실패 처리

- **설정상 비활성, 활성 목록 노출, 본문 열람, 지침 준수**는 서로 다른 증거다. 켜졌다는 사실만으로 모든 지침을 지켰다고 말하지 않는다.
- 이 실행 방식은 스킬 발견 설정과 대상·기존 스킬·실험 기록 경로의 읽기 권한을 분리한다. 시스템 전체의 모든 사본까지 격리했다고 표현하지 않는다. A에서 대상 본문 열람이나 상대 결과 접근이 관찰되면 유효한 OFF/ON 품질 비교로 판정하지 않는다.
- 자동 `$skill` 호출은 본문이 도구 호출 없이 주입될 수 있다. 도구 로그가 없다는 이유만으로 미적용이라 단정하지 않는다. 기본 러너는 관찰 가능한 본문 읽기 방식을 사용한다.
- 같은 모델·추론 설정과 공통 과제를 사용한다. 설정한 모델명과 확인된 실제 실행 정보를 구분한다. 단발 실행의 작은 차이를 일반적 성능 우위로 단정하지 않는다.
- CLI/활성 상태 확인이 실패하면 남은 파일을 보존하고 미검증 상태를 보고한다. 공유 카탈로그의 협업 에이전트로 조용히 대체하지 않는다. 재실행은 새 폴더에서 두 조건 모두 수행한다.
- 실패·누락·오염·사실 확인 불가에는 `undetermined`를 사용한다. 로그의 원문과 민감 정보는 로컬에 보존하고, HTML에 공개할 필드는 확인한다. 내부 추론 이벤트는 보고서에 표시하거나 평가하지 않는다.

## 기존 v1 자료

`prepare_run.py`, `capture_responses.py`, `render_report.py`와 [기존 규약](references/protocol.md)은 이전 ‘지침 추가 제공’ 실험의 재현용이다. 새 OFF/ON 로그 실험에 사용하지 않는다. v1 답변 화면은 실제 실행 기록이 아니며, 이를 새 실험의 증거로 재분류하지 않는다.
