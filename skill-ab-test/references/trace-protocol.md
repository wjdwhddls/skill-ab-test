# 스킬 구조 분석과 실제 실행 로그 비교 규약 (v2)

## 1. 분석과 비교의 의미

기본 목표는 선택한 스킬 하나의 구성과 작동 방식을 이해하는 것이다. 전체 소스의 정적 분석을 [skill-analysis.md](skill-analysis.md)에 따라 작성하고, A/B 실행은 그중 실제로 관찰한 경로와 결과를 확인하는 데 사용한다. 소스에 적힌 절차와 이번 실행에서 수행된 절차를 섞지 않는다. 이 규약의 실행 범위는 텍스트 응답과 필요한 읽기 작업이며, 파일 생성·코드 실행·외부 서비스 변경의 효과까지 입증하지 않는다.

현재 설치되지 않은 스킬만 대상으로 한다. 현재 목록과 알려진 로컬 스킬 경로의 이름(이름공간 포함)·원문 해시가 겹치면 모델 실행을 시작하지 않는다. 새 `codex exec` 프로세스 두 개를 동일 모델·추론 설정·공통 입력·읽기 전용 권한으로 실행한다. CWD는 A/B별로 분리하고 대상 파일은 B 폴더에만 둔다. A는 발견한 스킬을 모두 끄고, B는 고정한 대상 하나만 켠다. 별도 플러그인 카탈로그가 로컬 `skills/list`에 전부 나타나지 않을 수 있으므로 양쪽 모두 실행별 `features.plugins=false`, `features.remote_plugin=false`도 적용한다. 전역 설정·설치 파일은 변경하지 않는다. 각 조건의 사전 목록을 원본 RPC와 함께 보존한다.

B에만 ‘고정 SKILL.md를 읽고 적용하라’는 로딩 지시를 추가한다. 이 지시와 스킬 본문이 처리 조건이다. 공통 질문/입력은 동일하며 구조 분석 JSON·워크플로 요약·평가 기준은 응답 프로세스에 전달하지 않는다. 메인의 분석 파일은 두 작업 폴더 밖에 보관한다. 로딩 명령 차이 자체를 스킬이 자발적으로 개선한 결과로 보지 않는다.

이 구조는 대상·기존 스킬·실험 기록 경로의 파일 읽기를 샌드박스로 제한한다. `:read-only`를 상속하는 실행별 권한 프로필을 사용하고 관리 정책을 그대로 적용한 `codex sandbox` 검사에서 A 차단/B 허용을 확인한다. ENOENT를 차단 성공으로 세지 않고 EPERM/EACCES만 인정한다. 시스템 전체의 모든 사본을 격리한 것은 아니며 모델의 사전 지식과 스킬 비노출은 별개다. A에서 대상 파일이나 상대 결과를 읽었다면 비교 무결성을 확인하고 품질 판정을 보류한다. 스킬 활성화, 본문 읽기, 내용 준수는 각각 따로 판단한다.

## 2. 실행 파일

```text
runs/<unique-id>/
  trace-plan.json             메인이 사전에 작성한 질문·기준·모델
  skill-analysis.json         메인의 전체 파일·분기·도구 분석과 실제 관측 연결
  source/SKILL.md             commit으로 고정한 원문
  source/...                 선택 스킬 하위 폴더 전체, 원래 경로·바이트 보존
  workspace/baseline/         대상 스킬이 없는 A 작업 폴더
  workspace/treatment/.agents/skills/<name>/...  B의 임시 복사본
  eligibility.json           미설치 여부 조회 범위와 결과
  discovery/                 최초 읽기 전용 skills/list 관측
  arms/baseline/              A의 실제 출력
  arms/treatment/             B의 실제 출력
    inventory-rpc.jsonl      원본 조회 응답
    inventory.json           정규화한 활성 상태
    read-probe.json           실제 읽기 허용/거부 검사 결과
    prompt.txt               실제 stdin
    events.jsonl             codex exec --json 원본 stdout
    receipts.jsonl           행마다 부모가 받은 시각(서버 발생 시각 아님)
    stderr.txt               실제 stderr
    answer.txt               codex -o 최종 답변
  trace-run.json             명령·설정·시각·상태·해시
  trace-review.json          메인만 작성하는 해석·발췌·판정
  trace-report.html          실제 이벤트 기반 보고서
  native-captures.json       원본 로그 화면의 종류·시점·행·해시
  screenshots/              실제 로그 화면 캡처, 가능한 경우
```

실행 폴더는 항상 새로 만든다. 실패한 실행의 파일을 덮어쓰지 않는다. `source/`의 수집 단위는 선택한 스킬의 하위 폴더 전체이며 저장소 전체가 아니다. 스크립트·자산도 파일 목록에 포함하고 역할과 호출 지점을 정적으로 조사하되 임의로 실행하지 않는다. 스킬 밖 참조가 필요하면 원래 위치·고정 버전·수집 여부와 보존 경로를 명시한다. 원격 목록을 확인하지 못했다면 보존본 전체를 조사했다는 사실을 원격 폴더 전체 확인으로 확대하지 않는다. symlink를 사용하지 않고 인증 파일·사용자 전역 설정 사본을 실행 폴더에 담지 않는다.

새 실행에는 `skill-analysis.json`을 작성한다. 분석 계약의 버전은 `1`이며 실험·리뷰 계약의 버전 `2`와 별개다. 기존 실행에 분석 파일이 없는 경우의 로드 호환성을 위해 분석 로더는 선택적으로 읽지만, 이를 새 실행에서 구조 분석을 생략하는 근거로 쓰지 않는다.

## 3. 사전 계획

`trace-plan.json` 형식:

```json
{
  "schema_version": 2,
  "title": "스킬 이름 — 실행 절차 비교",
  "source": {
    "name": "skill-folder-name",
    "url": "https://github.com/owner/repo/blob/FULL_COMMIT/SKILL.md",
    "commit": "0123456789012345678901234567890123456789",
    "entrypoint": "source/SKILL.md"
  },
  "model": "환경에서 확인한 모델 식별자",
  "reasoning_effort": "환경에서 확인한 추론 설정",
  "cases": [
    {
      "id": "Q1",
      "title": "대표 사용 사례",
      "prompt": "사용자 요청",
      "input": "동일 입력 자료",
      "criteria": [{"id": "C1", "label": "판단 항목", "rule": "사전 판단 기준"}]
    },
    {
      "id": "Q2", "title": "복합 조건", "prompt": "사용자 요청", "input": "입력 자료",
      "criteria": [{"id": "C1", "label": "판단 항목", "rule": "사전 판단 기준"}]
    },
    {
      "id": "Q3", "title": "정보 부족", "prompt": "사용자 요청", "input": "입력 자료",
      "criteria": [{"id": "C1", "label": "판단 항목", "rule": "사전 판단 기준"}]
    }
  ]
}
```

모델을 추정해서 적지 않는다. 현재 실행 가능한 설정을 확인한 뒤 양쪽에 동일하게 고정한다. `model`은 요청값이며 서비스의 정확한 내부 버전까지 검증했다는 뜻이 아니다. 대상이 문서/코드/외부 서비스 실행 전용이라 텍스트 과제가 유효하지 않으면 평가 범위를 먼저 조정한다. 임의의 텍스트 문항으로 전체 스킬 효과를 평가하지 않는다.

질문에는 사용자가 달성하려는 목표와 동일한 자료를 제공한다. 스킬에 있는 단계·출력 정답·필수 확인 질문을 과제에 그대로 적어 양쪽에 가르치지 않는다. 자료 탐색이나 누락 확인을 검증하려면 그 행동이 필요한 동일 자료를 두 조건에 준다. 평가 기준과 정적 분석은 메인만 가진다. 각 문항이 어느 선언 분기를 시험하는지 메인이 확인하고, 포함되지 않은 분기는 `skill-analysis.json`에 이번 시험의 미관측 범위로 남긴다.

## 4. 수집

```bash
python3 "$skill_root/scripts/run_trace_pair.py" "$run_dir" --timeout 600
```

CLI가 없거나 사전 스킬 조회에 실패하면 원인을 보고하고 보존된 파일을 남긴다. 실행 성공을 만들어 내려고 사용자의 전역 파일을 이동하거나 삭제하지 않는다. CLI 상태 초기화/모델 연결에 환경 권한이 필요하면 해당 명령의 정상 승인 경로를 사용한다. 승인·정책·샌드박스를 무시하는 플래그는 사용하지 않는다.

`skills/list`는 실제 `exec`와 별도 프로세스에서 같은 설정으로 조회한 관측이다. 런타임 전체 본문 주입의 증명으로 확대하지 않는다. `--json`에는 도구 명령·MCP·파일 변경·메시지·실패 등이 나온다. 본문을 읽었다는 판단에는 성공한 호출과 실제 출력이 필요하다. ‘읽겠습니다’라는 중간 안내만으로 읽었다고 판정하지 않는다.

출력에 `reasoning` 유형이 있으면 원본은 그대로 보존하되 보고서 표시·인용·채점에서 제외한다. 공개 가능한 실행 행동을 비교하며 내부 사고 과정을 요구하거나 재구성하지 않는다. 보고서 전 원본 로그의 민감 정보 여부를 확인한다. 민감 정보가 있으면 원본을 수정하지 말고 별도 마스킹 표시본과 마스킹 사실을 남긴다. 현재 렌더러에 자동 비밀정보 탐지/마스킹 기능은 없다.

## 5. 메인의 판정

메인은 먼저 `skill-analysis.json`의 선언된 단계·서비스에 실제 로그 또는 답변 근거를 연결한다. 서비스가 문서에 등장했다는 사실, 사용 가능한 도구로 등록됐다는 사실, 실제 호출됐다는 사실을 각각 구분한다. `cat`으로 지침 파일을 읽은 기록은 그 파일의 모든 단계를 준수했다는 근거가 아니다. 선언된 검토 단계가 내부에서 수행됐다고 추정하지 않는다. 구조 설명과 실제 품질 판정은 서로 다른 자료이며, 아래 판정은 계속 메인이 직접 수행한다.

`trace-review.json`은 **메인이 직접** 작성한다. 본문 읽기 여부, 추가 도구/절차, 오류, 산출물/응답을 구분한다. 사전 기준으로 각 질문을 확인하되 화면에는 핵심 차이 3~6개를 권장한다. 항목 수를 맞추려고 차이를 만들어 내지 않는다. 동일 답변, 악화, 혼합 결과도 그대로 기록한다.

```json
{
  "schema_version": 2,
  "evaluated_by": {"role": "main", "agent_id": "/root"},
  "what": "처음 보는 사람이 이해할 짧은 용도 설명",
  "takeaway": "이번 실행에서 확인한 결론 한 문장",
  "workflow_summary": {
    "baseline": "관찰된 A 동작",
    "treatment": "관찰된 B 동작"
  },
  "integrity": {"validity": "verified", "notes": ["실제 로그로 확인한 범위"]},
  "differences": [
    {
      "title": "차이의 핵심",
      "verdict": "undetermined",
      "observed": "관찰 사실",
      "reason": "이 판정을 내린 이유. 로딩만으로 품질 개선은 판단하지 않는다.",
      "a": {"kind": "absence", "scope": "recorded_events", "note": "기록된 전체 이벤트에 대상 파일 읽기 호출 없음"},
      "b": {"kind": "event", "line": 4, "quote": "해당 실제 이벤트의 관측 필드에 정확히 존재하는 문자열"}
    }
  ],
  "limits": ["관찰 한계"]
}
```

- `verdict`: `improved` 개선, `worsened` 악화, `unchanged` 차이 없음, `undetermined` 판단 불가. 동작이 다르다는 사실과 더 낫다는 판정을 구분한다.
- `a`/`b`는 각각 baseline/treatment의 근거다. 이벤트는 **원본 JSONL 1부터 세는 행 번호**와 관측 필드의 정확한 부분 문자열. 답변은 `{ "kind":"answer", "quote":"정확한 발췌" }`.
- 없음은 `{ "kind":"absence", "scope":"recorded_events" 또는 "answer", "note":"확인 범위와 한계" }`. 기록 범위 안의 부재만 의미하며 미기록 행동까지 하지 않았다고 단정하지 않는다.
- `integrity.validity`: `verified`는 기록으로 확인한 설정과 관찰 범위 내 유효함, `limited`는 통제 증거 부족, `contaminated`는 대상/상대 응답 노출 확인. 후자 둘은 품질 판정을 `undetermined`로 한다.
- 실행 실패, 자료 부족, 독립 사실검증 불가를 악화로 바꾸지 않는다. 불확실한 기준은 `undetermined`로 남긴다.

## 6. 보고서 구조와 측정값

기본 산출물은 스킬 전체를 이해하고 실제 행동까지 추적할 수 있는 글래스 대시보드다. 첫 화면에서 스킬의 목적·입출력·작동 원리를 짧게 설명하고, 전체 구조·작동 흐름·도구와 전제·실제 A/B 실행·최종 판단으로 이동하게 한다. 긴 문서 전체를 세로로 나열하지 않는다.

- **전체 구조:** 고정 소스의 폴더 트리와 모든 파일을 표시한다. 파일을 선택하면 역할·읽거나 사용하는 조건·연결 파일·원문을 보여준다. 파일을 읽은 실행 근거가 있으면 함께 연결하고, 없으면 이번 실행에서 확인하지 못한 범위를 설명한다. 메타데이터·스크립트·자산·라이선스를 지침 파일과 구별한다.
- **작동 흐름:** 선언된 순서와 조건 분기를 소스 근거로 보여주고, 각 단계에 실제 이벤트·응답을 별도로 연결한다. 단계 사이 관계는 `next`를 따르며 분기를 단일 직렬 파이프라인으로 바꾸지 않는다. 원문에 흩어진 지침을 메인이 연결해 요약한 경우 그 사실을 밝힌다. 소스에 있으나 이번 과제로 실행되지 않은 분기도 남긴다.
- **도구와 전제:** 문서가 제안하는 서비스, 구체적으로 실행된 도구·명령, 환경 의존성을 구별한다. 어떤 단계에서 왜 필요한지와 접근 조건을 설명하고 선언 근거와 실행 근거를 따로 연결한다. 서비스 언급을 설치·인증·실제 호출의 증명으로 표시하지 않는다.
- **행동 비교:** 태블릿에서도 A/B를 나란히 두고 각 실행의 행동을 독립적으로 선택한다. 실제 관측된 순서와 원본 행을 사용한다. 서로 다른 이벤트를 같은 시각·동일 단계로 맞추거나, 로그에 없는 행동을 보충하지 않는다.
- **응답 비교:** 양쪽 원문을 함께 보여준다. 문항별 보기에서는 실제 응답의 명시된 문항 경계로만 나누며, 경계를 확인할 수 없으면 전체 응답을 유지한다.
- **최종 정리:** 메인이 작성한 항목명과 기존 네 종류 판정, 양쪽 발췌, 짧은 판정 이유를 함께 연결한다. 핵심 사실과 좁은 개선 범위를 우선 전달한다. 판정 개수를 승률이나 전체 성능 점수로 해석하지 않는다.
- **조건·한계:** 동일 조건/처리 차이와 확인된 차이/판단 불가를 나누어 표시한다. 직접 측정한 수치는 원본 근거와 함께 표시하고 긴 검증 기록은 접는다.
- **원본 로그:** 실제 캡처와 출처·시점을 보존한다. 보고서 UI 캡처를 실행 화면으로 분류하지 않는다.

근거 링크를 누르면 해당 탭과 행동·원문이 함께 열려야 한다. 조작은 터치와 키보드로 가능해야 하며, 좁은 화면은 A/B 순서를 유지해 세로로 배치한다. 스크립트 없이도 원문을 열람할 수 있는 기본 표시를 남긴다. 모바일에서 파일 링크가 코드로 보이면 같은 링크만 다시 주지 말고, 사용 가능한 대화 내 미리보기로 표시한다. 미리보기 용량 때문에 캡처를 분리하면 위치를 안내하고 원본 이미지 바이트와 캡처 설명은 유지한다.

아래 정보는 해당 탭 안에 보존한다.

1. **실험 조건:** A/B 열을 가진 표에 동일 모델 요청값·추론 설정·과제·권한과, 대상 스킬 등록/열람의 차이를 표시한다. 설정을 고정했다는 사실과 실제 지침 준수는 구분한다.
2. **실측 비교:** 원본 이벤트의 완료 도구 호출, 성공 출력에서 확인한 파일, `turn.completed.usage`의 입력/캐시/출력 토큰, 프로세스 시작~종료 경과 시간을 대조하고 각 수치에 근거를 연결한다. 양쪽 모두 값이 있는 항목만 비교표에 넣는다. 누락은 0으로 바꾸지 않으며 측정된 0은 유효하다. 캐시 입력은 전체 입력의 일부이며 다시 더하지 않는다.
3. **확인된 차이 / 아직 판단할 수 없는 것:** 메인이 별도로 작성한다. 관찰 차이와 품질 개선을 구분하고, 후자는 기존 네 종류 판정과 연결한다. 이번 결론에 영향을 주는 관찰 한계만 남긴다.

용어 설명이나 네 개념의 고정 섹션은 만들지 않는다. 소스에 선언된 구조와 지침은 원문으로 설명하고, 실행 경로와 관측 정보는 실제 행동·상태·오류·사용량 로그로 보여준다. 미실험 분기를 설명하는 것과 수집하지 않은 성능 지표를 카드로 채우는 것은 다르다. 사용 한도나 전체 비용도 실제 측정 출처·시각·단위·집계 범위가 있어야 표시할 수 있다. 수집하지 않은 한도·잔여량·요금·검토 시간은 보고서에서 생략하고, ‘미측정’ 행이나 설명 카드로 대신 채우지 않는다.

`trace-review.json`에 다음 `report_scope`를 추가한다. confirmed/unknown은 각각 최대 6개다. confirmed의 evidence는 양쪽 arm을 모두 포함하고 기존 exact quote/absence 규칙을 따른다.

```json
{
  "report_scope": {
    "confirmed": [{
      "topic": "실행 경로",
      "a": "A의 관측값",
      "b": "B의 관측값",
      "conclusion": "이 근거에서 확실히 확인되는 차이",
      "evidence": [
        {"arm":"baseline", "kind":"absence", "scope":"recorded_events", "note":"기록된 전체 이벤트의 확인 결과"},
        {"arm":"treatment", "kind":"event", "line":5, "quote":"해당 행에 있는 정확한 관측 필드 발췌"}
      ]
    }],
    "unknown": [{
      "topic":"반복 안정성",
      "missing":"반복 실행 기록",
      "why":"조건별 한 번의 실행으로는 재현성을 판단할 수 없음",
      "next_check":"동일 조건에서 반복 실행해 관찰 차이가 유지되는지 확인"
    }]
  }
}
```

```bash
python3 "$skill_root/scripts/trace_report.py" "$run_dir"
```

## 7. 원본 로그 화면 캡처

우선 원래 에이전트의 실행 UI 또는 실제 터미널 출력을 촬영한다. 컴퓨터 사용 도구로 접근할 수 없다면 제한을 알리고, **원본 JSONL 파일을 브라우저에서 직접 열어** 촬영할 수 있다. 이 경우 원본 바이트를 `text/plain`으로 제공하며, 비교 보고서·새 로그용 HTML 템플릿으로 대체하지 않는다. 가능하면 직접 연 파일의 응답 바이트/해시와 보존된 원본을 대조한다.

- `native_agent_ui`: 실제 에이전트 UI.
- `live_runner_terminal`: 실행 중인 러너 터미널.
- `saved_log_terminal`: 종료 후 저장된 원본을 터미널에서 열람.
- `raw_log_browser`: 종료 후 원본 JSONL 파일을 브라우저에서 직접 열람.

실시간 캡처와 종료 후 열람을 섞어 표현하지 않는다. 촬영 가능한 화면이 없으면 미촬영으로 남긴다. 보고서 HTML 캡처는 별도의 디자인 검수용일 뿐 이 목록에 등록하지 않는다. 내부 추론 항목이나 민감 정보가 화면에 나타나지 않게 촬영 범위를 확인한다. 단순히 숨겨 놓고 전체 원문을 공개하는 방식으로 처리하지 않는다.

```bash
python3 "$skill_root/scripts/native_captures.py" "$run_dir" \
  --image screenshots/raw-A.png --title "A 원본 로그 파일" \
  --captured-at "실제 촬영 ISO8601 시각" --surface "브라우저 원본 JSONL" \
  --basis raw_log_browser --arm baseline \
  --source-file arms/baseline/events.jsonl --visible-lines "1:4" \
  --display-command "원본 JSONL URL 직접 열람" \
  --page-url "실제로 연 원본 파일의 URL"
python3 "$skill_root/scripts/trace_report.py" "$run_dir"
```

`native-captures.json`은 이미지와 실행 원본의 해시를 묶는다. 메인의 분석 문구나 보고서 디자인 수정은 실제 로그 화면을 바꾸지 않으므로 리뷰/HTML 해시에는 묶지 않는다. 스크린샷은 원본 근거를 보조하며 파일·행 범위·호출 결과가 비교의 근거다. `trace_captures.py`와 기존 `trace-captures.json`은 이전 보고서 미리보기 재현용이며 새 원본 캡처에 사용하지 않는다.

최종 전달에는 HTML, 원본 캡처 출처, 확인한 차이, 해석에 필요한 관찰 한계를 짧게 포함한다. 측정하지 않은 지표를 나열하지 않는다. 원래 앱의 실시간 화면을 확보하지 못했다면 그 사실을 명확히 남긴다.
